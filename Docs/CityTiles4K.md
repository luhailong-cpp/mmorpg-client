# 主城 4K 分块加载接入

## 当前三张日景地图的分片交付（2026-10-25）

正式联机地图已使用 `CurrentMaps20261009` 的主城、东海渔村、八仙岛布局。按用户当前要求，完整已生成的原生 4096×4096 分片先接入，内部或外沿接缝待修不再阻止使用。清单为各地图目录下的 `tiles.json`，交付状态为 `partial_native_tiles`，选择策略为 `all_generated_current_layout`。主城采用 16×16 网格，渔村和八仙岛采用 14×14 网格；每张清单绑定现有 `source.json` 的布局 SHA-256。仍须核对完整图像、图格身份、尺寸和原图哈希；只有部分 CORE 且混有占位布局的工作预览不覆盖完整图。QA 的失败、未知和未正式验收状态如实保留，接入不代表接缝通过。

原始 PNG、来源与检查记录和 Unity 元数据随客户端 Git 提交。运行不依赖本机美术目录；普通完整检出或包含 `Assets/Resources/World/CurrentMaps20261009` 的稀疏检出即可取得资源。拉取新版本后须重新导入/构建客户端，已生成的旧安装包不会自动增加资源。

本批共 **519 张**原始 4096×4096 PNG：主城 **178 张**、渔村 **165 张**、八仙岛 **176 张**，合计 **13,108,398,493 字节**。资源导入及全量仓库校验已通过；内部 QA 为 131 张通过、50 张失败、338 张未确认，整图尚未验收，也未做实机画面验证。源图包含 518 张 RGB 和 1 张全不透明 RGBA，均保留原始 PNG 字节；具体证据见[本次资源记录](VerificationEvidence/generated-map-tiles-20261025/resources.json)。

空间候选查询使用 C++ 服务端 `GridSystem` 同源的六边形算法，采用 Amit Patel / Red Blob Games 的[官方 C# 实现](https://www.redblobgames.com/grids/hexagons/codegen/output/lib.cs)，保留 CC0 来源与原文件 SHA。布局为固定 20 个服务器世界单位的平顶六边形（flat-top），原点为 `(0,0)`；原作者代码的半值舍入显式改为 `AwayFromZero`，与服务器 C++ `round` 一致。坐标统一经过 `WorldCoordinateConverter`，即服务器 X 对应 Unity Z、服务器 Y 对应 Unity X；详见[来源及改动说明](../Assets/Scripts/World/CurrentMaps/RedBlobHexGrid.NOTICE.txt)。

加载候选来自玩家脚下所在格加六个邻格，共七格；相机实际视野覆盖的其他六边形也纳入查询，避免宽屏、缩放或镜头偏移漏片。原有 16×16／14×14 PNG 分片保持不变，不把全图改切成九块。初始化仅根据分片矩形元数据建立稀疏空间索引，每张方形分片登记到与其多边形相交的全部六边形；初始化不读取 PNG，图片只在异步请求时加载。

七格周边查询与六张纹理预算分别控制空间候选和内存，数量不能互相替代。共享纹理池最多六张（包含尚未完成、不可取消的请求），最多两个并发请求。可见中心优先，空余名额预取前进方向的相邻块；无压力时离开两秒后释放，满额时已不需要的完成块立即为新可见块腾位。六张原始 RGB24 像素数据约 288 MiB，比原八张减少 25%；这不是整客户端或实际 GPU 内存测量。超过纹理预算、尚未交付或加载失败的位置仍显示当前同版布局底图。退出地图释放分片，跨图未完成请求也继续占预算。

本次只增加同版布局的细节层，世界矩形、出生点和客户端/服务端导航保持一致。可移植交付校验命令为 `python tools/import_completed_map_tiles.py --verify`；数量、来源与验证边界见[本次交付记录](VerificationEvidence/generated-map-tiles-20261025/README.md)。后面的章节保留旧 `CityTiles4K` 完整发布管线及历史验证记录，不代表当前三张地图的资源状态。

## 资源合同

- 每个交付块必须为 `4096 × 4096`，运行时也检查实际导入尺寸。
- 加载器支持不同方形网格；**当前生产交付固定为16×16、256块、65536×65536像素**。生产发布工具不接受其他尺寸。
- 入口为 `Assets/Resources/World/CityTiles4K/{city}/{variant}/manifest.json`。
- `city` 为 `tianyong`、`penglai`、`donghai`、`lanxian`；后三者支持 `day` 和 `festival`。目前天墉正式底图为节庆版，对应 `tianyong/festival`。
- `tiles` 是完整行优先字符串数组，起点为西北角，行向南增长。资源路径不含 `Assets/Resources/` 与扩展名，例如 `World/CityTiles4K/tianyong/festival/tiles/r01_c01`。
- JSON 字段为 `schemaVersion: 1`、`tilePixels: 4096`、`columns`、`rows`、`worldRect`、`tiles`、`legacyForegroundCompatible`。
- 当前 `worldRect` 必须为 `{ "x": 50, "y": 0, "width": 300, "height": 300 }`。这里 `y` 表示 Unity 世界 Z 的最小值，保持现有导航、出生点和场景协议坐标。
- 方块在世界中保持等比；`columns / rows` 必须等于世界宽高比。当前300 × 300世界地图使用16×16方形网格，`worldRect.y` 仍表示世界Z。
- 天墉额外要求 `legacyForegroundCompatible: true`，表示新稿已经通过现有前景剪影逐一验收；未声明时不启用。
- 不完整数组、重复路径、无效尺寸、错误世界范围不会启用。图片缺失或不满足 4096 尺寸时保留旧底图并报告错误。

## 加载与清理

生产运行时与离线 sandbox 在相机更新后计算真实视口与地面交点，加载覆盖视口的所有块，并预载一圈邻块。视口跨越多个块时会超过九块；不会用固定 3 × 3 数量造成超宽屏或缩放后的空洞。

先加载屏幕内且靠近中心的块，再加载周边块。资源请求最多同时两个，已离开场景但尚未完成的请求也计入上限。离开预载范围两秒后释放贴图、网格对象和材质，避免边界来回移动导致频繁重复加载。共享引用计数保证切场景时旧请求完成不会释放新场景仍在使用的同一纹理。

高清层覆盖既有底图；旧图保留，避免缺图、请求失败或等待加载时出现黑块。这意味着仍存在旧图常驻的开销，不能把新增功能表述为已完成所有移动端内存优化。

## 日景与节庆原子切换

换景时保留当前高清层和当前底图，目标层先在隐藏节点中准备。每帧使用相机移动、缩放之后的最新视野，只有该视野必需块全部完成尺寸验证及网格创建，才在同一帧提交新高清层、底图、角色光照和外观状态。候选缺图、尺寸错误、激活异常、取消或地图销毁时保留当前画面并清理候选；快速切回当前景色不会执行已取消目标的回调。

两边都尚无高清 manifest 时，原有底图仍立即切换，保持现有客户端行为。已有高清层而目标 manifest 缺失时，保留当前高清画面并报告错误，不降成目标低清图。候选只准备当前视野必需块，激活后恢复邻块预载；切换期间显存会同时容纳当前层和候选可见块，仍需在目标设备测量峰值。

## 导入与验收

新路径导入为 Default / 2D / 最大 4096 / NPOT None / Clamp / Bilinear / sRGB / 不可读 / RGB24 无压缩。平台覆盖设置清空，避免复制旧 `.meta` 后悄悄降成 2048。CPU 不保留可读副本。单块 RGB24 的像素数据约 48 MiB；实际 GPU 驻留应按目标设备测量。

交付合同目前没有独立 mip 的边缘扩展，故禁用 mipmap。后续若引入 mipmap 或 BC7 / ASTC 等 GPU 压缩，需另行验证边缘、细节与设备显存，不可通过降低源图分辨率替代验收。

天墉现有前景剪影与遮挡排序源自旧 6144 像素地图。发布新的完整 manifest 前，必须用新图逐一核对剪影形状、光照、色调、脚点和最近景清晰度。旧1024切片不能以仅坐标兼容为由遮盖新4K细节；未满足近景清晰度时，应先交付相应高清前景再声明兼容。如发生变化，应重做对应前景，而非将旧剪影覆盖在新画面上宣称验收完成。导航仍与原布局一致，路径位置变化也需要独立更新并验证。
